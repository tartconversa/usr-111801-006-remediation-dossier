# 景区资料协作台账：整改材料的闭环与撤销血缘

服务登记资料来源、字段、原件、使用许可、数据产品与交付凭据。示例主体和记录均为虚构，不连接真实文旅部门。

需要 Python 3.10 或更新版本，不依赖第三方包。

运行项目测试：python -m unittest discover -s tests -v。
检查源码：python -m compileall -q exchange。
运行本地演练：python -m exchange --database demo.db。

exchange/catalog.py 登记来源字段和原件，grants.py 与 policy.py 管理使用边界，products.py 编排资料，delivery.py 出具回执，audit.py 记录操作。现有接口只覆盖单次登记、编排和交付，目录职责及当前边界可从源码与测试读取。

## 整改复核的逐项追溯

exchange/rectification.py 在同一台账内建立整改要求、提交材料与复核决定的逐项可追溯关系：

- 整改案件拆成带序号的要求项（设施、服务、安全等），每个原问题独立跟踪，结论不互相连带。
- 材料按要求项形成不可变版本链：补交生成新版本，只把旧版本标记为 superseded，被退回的原件内容、摘要与对应批次均保留。
- 复核逐要求项挂接到具体材料版本，记录审核者、决定（pass/return）、理由与时间；撤销是软撤销，保留原判断并记录撤销人、时间和原因。
- 要求项与案件结论均由当前有效复核实时推导，不回写状态字段：局部通过不会使其他问题自动通过；撤销一次复核后，案件结论立即重新暴露缺口，并阻断新的拟发布结论。
- 拟发布结论生成逐项快照（要求、材料版本、审核者、理由、复核时间）并留存摘要；撤销后历史快照可通过 `currently_valid` 识别为不再被当前证据支持。
- `requirement_trace` 从结论一路查回要求描述、全部证据版本与审核者当时的判断；所有动作写入 audit 血缘。

覆盖这些规则的测试见 tests/test_rectification.py。
